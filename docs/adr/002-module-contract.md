# ADR-002: 显式清单模块注册

- 状态：已接受（2026-09-04）
- 影响范围：模块装配、启动行为、测试策略

## 背景

基座的核心承诺是"增量接入"：新 agent 模块**不改基座一行代码**即可挂载。
可选注册方式：

| 方案 | 说明 | 主要风险 |
| --- | --- | --- |
| A 包自动扫描 | `importlib.walk_packages` 自动发现 `modules/` 下所有模块 | import 副作用不可控，坏模块传染，装配顺序不确定 |
| B 装饰器注册 | `@register` 在模块 import 时生效 | 注册时机隐藏在 import 里，与 A 同源问题 |
| C 显式清单 | 配置声明 `AGENT_MODULES=chat,writer` | 需要手动维护一行配置 |

## 决策

采用 **C 显式清单**：

- `AGENT_MODULES` 环境变量为模块装配的**唯一事实源**（逗号分隔，顺序即装配顺序）
- 注册器（阶段 1 落地，`core/registry.py`）职责：
  1. 查重名——冲突即启动失败
  2. 校验 `AgentModule` 契约实现
  3. 未知模块名——启动即失败（fail-fast），绝不静默跳过
- 模块物理位置固定为 `src/agent_base/modules/<name>/`，但"存在于代码库"≠"运行时启用"

## 理由

- **可预测**：启动时装配哪些模块一目了然，可 diff、可 review
- **可测试**：测试显式构造清单，不依赖 import 副作用
- **生产安全**：一个坏模块不会因"被扫到"而拖垮整个进程；显式启用才会失败
- **失败语义清晰**：未知模块名 = 配置错误 = 立即失败
- 顺序语义免费获得：清单顺序即装配顺序

## 后果

- 负：新增模块要改一行配置（接受的代价）
- 未来若出现"模块很多、清单维护痛苦"的场景，可再评审此决策（届时加自动扫描的
  受控变体），但当前基座规模下显式性远优于便利性
